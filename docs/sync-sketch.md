# סקיצה: סנכרון עם אתר המכלול

מסמך זה הוא סקיצה בלבד. שום דבר ממנו עדיין לא ממומש: בתפריט "סנכרון" יש כרגע רק פריטים מנוטרלים.

## החלטות שהתקבלו

| נושא | החלטה |
|------|-------|
| כיוון | דו־כיווני בסוף הפיתוח: התוכן יורד מהאתר, ועריכות מקומיות עולות אליו |
| הודעות | המשתמש מקבל באפליקציה את ההודעות שלו מהאתר |
| טעינת תוכן | מקובצי dump שהאתר יפרסם |
| היקף | בחירה לפי נושאים, על בסיס קובצי ה-dump |
| תמונות | אפשרות, לא חובה. תקציב דיסק: 10GB |
| פנייה לאתר | ישירה, אבל לא סנכרון קבוע. רק ההודעות נבדקות בתדירות קבועה |
| גרסת מדיה־ויקי | הגרסה המקומית תעלה לזו של האתר |
| התחברות | OAuth. ההרחבה מותקנת באתר, ואפשר לרשום בה יישומים חדשים |

## נתוני פתיחה

נבדקו מול ה-API של האתר ב-12 בנובמבר 2026:

| נתון | ערך | משמעות |
|------|-----|--------|
| גרסת מדיה־ויקי באתר | 1.46.2 | האפליקציה מתקינה 1.43 LTS, ולכן נדרש שדרוג |
| עריכות ביממה (11 בנובמבר) | 294, מהן 41 דפים חדשים | עדכון בין dump ל-dump הוא קטן |
| תגיות עריכה | `visualeditor`, `discussiontools`, `disambiguator`, `wikiimport` | האתר נשען על הרחבות שאינן בהתקנה הבסיסית |
| יומן ייבוא | ייבוא בין־ויקי של תבניות ויחידות (למשל `יחידה:Navbox`) | התוכן תלוי ב-Scribunto ובתבניות רבות |

מספר הדפים הכולל ונפח התמונות עדיין לא נמדדו.

## ארבעת הרכיבים

הסנכרון מתחלק לארבעה רכיבים שכמעט אינם תלויים זה בזה:

1. **התאמה לאתר**: גרסה, הרחבות והגדרות. תנאי לכל השאר.
2. **תוכן מהאתר**: חבילות נושא מקובצי dump, ועדכון ידני ביניהן.
3. **הודעות**: הרכיב היחיד שפונה לאתר בתדירות קבועה.
4. **העלאת עריכות**: האחרון, והיחיד שכותב לאתר.

## 1. התאמה לאתר

- **גרסה**: `src/versions.js` יעבור לגרסת האתר. 1.46 אינה LTS, ולכן האפליקציה תצטרך לעקוב אחרי שדרוגי האתר ולא רק אחרי עדכוני אבטחה.
- **שדרוג ויקי מותקן**: היום הוא לא נתמך. נדרש מסלול שמחליף את קובצי מדיה־ויקי, מריץ `update.php`, ושומר את `LocalSettings.php`, התמונות ומסד הנתונים. בלי זה כל שדרוג באתר ישבור את ההתקנות הקיימות.
- **בדיקת התאמה**: לפני כל ייבוא האפליקציה משווה את הגרסה המקומית לזו שרשומה בחבילה, ומסרבת לייבא חבילה שנוצרה בגרסה חדשה יותר.
- **הרחבות**: להתקין מקומית את ההרחבות שהתבניות תלויות בהן (לפחות Scribunto, ‏ParserFunctions, ‏TemplateStyles, ‏Cite). הרשימה המלאה תילקח מ-`siteinfo` של האתר. הרחבות שאינן חלק מחבילת מדיה־ויקי יצטרכו מקור הורדה משלהן.
- **דרישות PHP** של הגרסה החדשה צריכות בדיקה מול `src/versions.js` ומול הבדיקה של PHP מותקן.

## 2. תוכן מהאתר

### חבילות נושא

האתר מפרסם קובץ מניפסט אחד ולצדו קובצי dump. האפליקציה מורידה את המניפסט, מציגה את הנושאים, והמשתמש בוחר.

מבנה מוצע למניפסט:

```json
{
  "mediawikiVersion": "1.46.2",
  "generated": "2026-11-12T00:00:00Z",
  "packages": [
    {
      "id": "base",
      "title": "תבניות, יחידות והודעות ממשק",
      "required": true,
      "pages": { "url": "base-pages.xml.gz", "size": 0, "sha256": "" }
    },
    {
      "id": "history",
      "title": "היסטוריה",
      "requires": ["base"],
      "pages": { "url": "history-pages.xml.gz", "size": 0, "sha256": "" },
      "images": { "url": "history-images.tar", "size": 0, "sha256": "" }
    }
  ]
}
```

- **חבילת בסיס** אחת היא חובה: תבניות, יחידות, קטגוריות ומרחב `מדיה ויקי`. בלעדיה אף ערך לא נראה נכון.
- **חבילת נושא** מכילה את הגרסה האחרונה של כל ערך, בלי היסטוריה, דפי שיחה או דפי משתמש.
- ערך ששייך לשני נושאים מופיע בשתי החבילות, והייבוא מדלג על מה שכבר קיים באותה גרסה.
- כל קובץ נבדק מול ה-`sha256` שלו לפני ייבוא, והורדה שנקטעה ממשיכה מהמקום שבו עצרה.
- הייבוא רץ ב-`importDump.php`, ואחריו `rebuildrecentchanges.php` ו-`initSiteStats.php`.

איך מחלקים את האתר לנושאים (לפי קטגוריות־על, פורטלים או רשימה ידנית) היא החלטה של מפעילי האתר, כי הם אלה שמייצרים את הקבצים.

### תמונות

- קובץ תמונות נפרד לכל חבילה, עם תמונות מוקטנות בלבד. המשתמש מסמן לכל נושא אם הוא רוצה אותן.
- **תקציב 10GB**: מסך הבחירה מציג את הנפח המצטבר של מה שסומן לפי הגדלים שבמניפסט, ולא מאפשר לחרוג מהתקציב. התקציב ניתן לשינוי בהגדרות.
- תמונה שלא הורדה נטענת מהאתר כשיש חיבור (`$wgForeignFileRepos`), ובלי חיבור היא חסרה.

### עדכון

אין סנכרון תוכן ברקע. שתי פעולות ידניות:

- **חבילה חדשה**: כשהמניפסט מציג תאריך חדש יותר לחבילה מותקנת, המשתמש יכול להוריד אותה מחדש.
- **עדכון עכשיו**: משיכת השינויים מאז תאריך החבילה דרך `recentchanges`, רק עבור דפים שכבר קיימים מקומית. מחיקות והעברות נקראות מ-`logevents`. `recentchanges` שומר בדרך כלל כ-90 יום, ומעבר לזה צריך חבילה חדשה.

## 3. הודעות

זה הרכיב היחיד שפונה לאתר בלי פעולה של המשתמש.

- **מה נמשך**: ההתראות של המשתמש באתר (אזכורים, הודעות בדף השיחה, תודות) דרך ה-API של ההתראות.
- **תדירות**: קבועה וניתנת לשינוי, למשל כל 15 דקות, ורק כשהאפליקציה פתוחה ויש חיבור.
- **תצוגה**: מונה בסרגל העליון, רשימה בחלון, והתראת מערכת. לחיצה על הודעה פותחת את הדף באתר בדפדפן החיצוני, כי דפי שיחה אינם בעותק המקומי.
- **סימון כנקרא** מקומית בלבד בשלב הראשון. סימון באתר הוא כתיבה, ושייך לרכיב 4.

### התחברות

גם ההודעות וגם העלאת העריכות דורשות חשבון באתר, ולכן ההתחברות נבנית כבר כאן. היא נעשית ב-OAuth, כך שהאפליקציה לעולם לא רואה את הסיסמה של המשתמש, והוא יכול לבטל את הגישה מהאתר בכל רגע.

**רישום היישום באתר** (פעולה חד־פעמית, ב-`Special:OAuthConsumerRegistration`):

- OAuth 2.0, יישום שאינו חסוי (בלי סוד לקוח). אפליקציית שולחן עבודה מופצת למשתמשים, ולכן סוד שמוטמע בה אינו סוד.
- כתובת חזרה: `http://127.0.0.1:<פורט קבוע>/oauth/callback`.
- הרשאות: בשלב ההודעות קריאה בלבד. הרשאות עריכה ויצירת דפים נדרשות רק לרכיב 4.

הרשאות של יישום רשום אינן ניתנות להרחבה אחרי האישור. לכן יש שתי דרכים: לרשום כבר עכשיו יישום אחד עם הרשאות העריכה, או לרשום יישום שני כשיגיע רכיב 4, ואז כל המשתמשים יאשרו מחדש. ההמלצה היא יישום אחד, כדי שהמשתמש יאשר פעם אחת.

**מהלך ההתחברות:**

1. המשתמש בוחר "התחברות" בתפריט. האפליקציה פותחת את דף האישור של האתר בדפדפן החיצוני, עם PKCE ועם ערך `state` אקראי.
2. האפליקציה מאזינה זמנית על הפורט הקבוע, בכתובת `127.0.0.1` בלבד, ומקבלת את קוד האישור כשהאתר מחזיר אליה את הדפדפן.
3. היא בודקת את ה-`state`, מחליפה את הקוד באסימון גישה ובאסימון רענון, וסוגרת את ההאזנה.
4. האסימונים נשמרים מוצפנים דרך `safeStorage` של Electron, לא בקובץ גלוי.
5. אסימון הגישה מתחדש אוטומטית. אם הרענון נכשל (למשל כי המשתמש ביטל את הגישה באתר), האפליקציה חוזרת למצב "לא מחובר" ומבקשת להתחבר שוב.

ההתחברות נעשית בדפדפן החיצוני ולא בחלון של האפליקציה, כדי שהמשתמש יזין את הסיסמה בדפדפן שהוא סומך עליו ויוכל להשתמש במנהל הסיסמאות שלו.

צריך לבדוק בטופס הרישום: איזו הרשאה מכסה קריאת התראות, האם כתובת חזרה ב-`http://127.0.0.1` מתקבלת, ומה אורך החיים של האסימונים.

## 4. העלאת עריכות

- כל דף מיובא שומר את מזהה הגרסה באתר שממנה יובא.
- עריכה מקומית בדף כזה נרשמת בתור העלאה, יחד עם גרסת הבסיס.
- **העלאה היא תמיד ידנית**: המשתמש פותח את רשימת העריכות הממתינות, רואה השוואה לכל אחת, ובוחר מה לשלוח.
- בשליחה נשלח `baserevid`. אם הדף השתנה באתר בינתיים, העריכה לא נשלחת: המשתמש רואה את שלוש הגרסאות ומחליט אם למזג, לדרוס את שלו או לוותר.
- העריכה עולה תחת שם המשתמש שלו, עם תגית עריכה ייעודית כדי שיהיה אפשר לזהות באתר עריכות שהגיעו מהאפליקציה. יצירת התגית דורשת פעולה של מפעילי האתר.
- **עדכון תוכן מול עריכה ממתינה**: עדכון או חבילה חדשה לא דורסים דף שיש לו עריכה ממתינה. הדף מסומן כהתנגשות ומטופל באותו מסך.
- דף חדש שנוצר מקומית עולה רק אם אין באתר דף באותו שם.

## מבנה מוצע בקוד

```
src/sync/
├── remote-api.js     # לקוח ל-API של האתר: המשך, הגבלת קצב, maxlag, ניסיון חוזר
├── account.js        # התחברות ב-OAuth, שמירה וחידוש של האסימונים
├── manifest.js       # הורדה ואימות של המניפסט, חישוב נפח מול התקציב
├── packages.js       # הורדה, אימות וייבוא של חבילות ותמונות
├── updates.js        # "עדכון עכשיו" דרך recentchanges
├── notifications.js  # בדיקה תקופתית של התראות
├── outbox.js         # תור העריכות הממתינות והעלאתן
└── state.js          # מצב הסנכרון
```

- הכול רץ בתהליך הראשי. ייבוא ועדכון דורשים שהשרתים המקומיים יפעלו; הודעות לא.
- מצב הסנכרון נשמר ב-`data/sync-state.json`, לצד `run-state.json`.
- בבדיקות: שרת מדומה שמגיש מניפסט, חבילות ו-API, כמו שרתי הדמה הקיימים, כך ששום בדיקה לא פונה לאתר האמיתי.

## ממשק

תפריט "סנכרון":

- חשבון באתר: התחברות וניתוק
- נושאים ותמונות: בחירה, הורדה וניצול התקציב
- עדכן תוכן עכשיו
- עריכות ממתינות להעלאה
- הודעות
- הגדרות: תדירות בדיקת ההודעות, תקציב דיסק

הורדה וייבוא מציגים התקדמות בסרגל העליון, ניתנים לעצירה, ואינם חוסמים את הגלישה בוויקי.

## סדר עבודה מוצע

1. שדרוג גרסה: מסלול שדרוג לוויקי מותקן, ומעבר לגרסת האתר.
2. הרחבות והגדרות, ובדיקה ידנית שדף מיובא אחד נראה כמו באתר.
3. חבילות: מניפסט, חבילת בסיס וחבילת נושא אחת, בלי תמונות.
4. תמונות ותקציב.
5. חשבון והודעות.
6. עדכון עכשיו.
7. העלאת עריכות.

שלבים 1 ו-2 אינם תלויים באתר ואפשר להתחיל בהם מיד. שלב 3 תלוי בפורמט החבילות.

## מה נדרש ממפעילי האתר

1. פרסום מניפסט וקובצי dump לפי נושאים, כולל חבילת בסיס, ובאיזו תדירות.
2. קובצי תמונות מוקטנות לכל נושא, ובאיזה רוחב.
3. כתובת קבועה שממנה האפליקציה מורידה את הקבצים.
4. רישום ואישור של האפליקציה כיישום OAuth, עם ההרשאות שסוכמו.
5. תגית עריכה לעריכות שמגיעות מהאפליקציה.
6. הודעה מראש על שדרוג גרסה באתר, כדי שהאפליקציה תתעדכן לפני שהחבילות החדשות מתפרסמות.

## שאלות פתוחות

1. איך מחלקים את האתר לנושאים, ומי מחליט?
2. מה קורה לעריכה מקומית בדף שאינו קיים באתר בכלל, למשל טיוטה אישית: האם היא נשארת מקומית בלבד?
3. האם ההודעות צריכות להגיע גם כשהשרתים המקומיים כבויים והחלון סגור (אפליקציה במגש המערכת)?
4. האם משתמש בלי חשבון באתר יכול להשתמש באפליקציה לקריאה בלבד?
